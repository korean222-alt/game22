# 소셜게임 스토리 3D — 게임 개발 계획서

원작 `소셜게임 스토리`(Kairosoft, Social Dev Story)의 2D 도트 경영 시뮬레이션을
**실시간 3D**로 옮긴다. 리서치 근거는 [RESEARCH.md](./RESEARCH.md).

---

## 0. 무엇을 만드는가

> 당신은 오늘부터 사장님이다.
> 층층이 쌓인 사무실에 직원을 앉히고, 기획서를 뽑고,
> **아이디어와 싸워** 게임을 완성하고, 출시해서 유저를 모은다.

- 픽셀 아이소메트릭 → **WebGL2 PBR 렌더링**
- 2D 스프라이트 직원 → **16본 스켈레톤 리깅 캐릭터**
- 평면 사무실 → **층을 쌓아 올리는 3D 오피스 타워**
- 개발 진행 바 → **턴제 개발 배틀을 3D 사무실에서 눈으로 본다**

## 1. 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 렌더러 | 직접 짠 WebGL2 | 의존성 0, 프로시저럴 머티리얼로 텍스처 에셋 불필요 |
| 모듈 | 네이티브 ES Modules | 빌드 스텝 없음. 정적 서버만 있으면 실행 |
| 상태 | 순수 JS 객체 + localStorage | 세이브가 곧 JSON |
| UI | DOM 오버레이 | 3D 캔버스 위에 얹는 편이 텍스트가 선명함 |
| 언어 | 한국어 우선 | 원작 한국어판 기준 |

빌드 툴체인을 두지 않는 것이 의도적인 선택이다. `python3 -m http.server` 하나면 돈다.

## 2. 그래픽 — "더 사실적으로"

기반이 된 Dunder Mifflin 3D 엔진은 **Blinn-Phong + LDR**이었다.
사실감을 위해 렌더 파이프라인을 통째로 교체한다.

| 항목 | 이전 | 3D판 |
|---|---|---|
| 라이팅 | Blinn-Phong | **Cook-Torrance GGX PBR** (metallic/roughness) |
| 프레임버퍼 | RGBA8 (LDR) | **RGBA16F HDR** |
| 블룸 | 없음 | **브라이트패스 + 5단 다운/업샘플 블러** |
| 그림자 | 3×3 PCF | **12탭 포아송 PCF + 회전 커널 + 슬로프 바이어스** |
| 노멀 | 지오메트리 노멀 | **프로시저럴 하이트에서 유도한 범프 노멀** |
| 앰비언트 | 반구 상수 | **하늘 irradiance + 러프니스별 스펙큘러 근사(IBL 유사)** |
| 이미시브 | 없음 | **모니터·조명이 블룸에 기여** |
| 톤매핑 | ACES | **노출 제어 + ACES + 필름 그레인 + 비네트** |
| AA | FXAA | FXAA 유지 (HDR 해소 후 적용) |

머티리얼은 여전히 **프로시저럴**이다. 텍스처 파일 없이 셰이더 안에서
카펫 섬유, 나뭇결, 브러시드 메탈, 직물, 아크릴 천장타일, 피부, 머리카락을 만든다.
PBR로 가면서 각 머티리얼이 `(albedo, roughness, metallic, emissive, bumpScale)`을 갖는다.

## 3. 게임 시스템

### 3.1 회사 상태

```
자금 (₩)   코인 (🪙)   랭크 (1~50)   스태미나 (일일 행동력)
연차/월/주  팬 수      명성          플랫폼 지식
```

랭크가 게이트하는 것: 자금 상한, 직원 정원, 의욕 상한, 해금 층수, 해금 수익모델.

### 3.2 직원

5개 기본 능력치.

```
기획 PLAN  프로그래밍 PROG  그래픽 GRAPH  사운드 SOUND  소셜 SOCIAL
```

직업별 기여 (원작 준수):

| 직업 | 화제성 | 조작성 | 임팩트 | 소셜 | 지속성 | 기획서 |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| 프로그래머 | ● | ● | | | | |
| 디자이너 | | | ● | | | |
| 사운드 | ● | | ● | | | |
| 네트워커 | | | | ● | ● | |
| 기획자 | | | | | | ● |

- **의욕(Motivation)**: 1당 +0.5% 배율. 자기 기획서로 완성하면 +1. 상한은 랭크 연동.
- **성장**: 아이템 지급 → 레벨업. 비용은 받는 사람의 레벨에 비례하고 **스태미나 1**이 든다
  (육성과 개발이 같은 자원을 놓고 다투게 하려는 것). 아이템 3종 + 만렙 → **전직**.
- **최고 직급 만렙 → 환생**: 직업 변경, 보너스/레벨 리셋, 재능 배율은 유지되고 ×1.12 된다.
  (만렙은 직급별 30 / 60 / 90)

### 3.3 개발 배틀 ★ 핵심

원작의 시그니처. 3D판에서는 **사무실 전체가 배틀 필드**가 된다.

```
1. 플랫폼 선택
2. 기획서 선택      (장르 × 내용, 등급 ★1~5)
3. 수익 모델 선택   (유료 / 부분유료 / 부분유료 장기운영)
4. ── 배틀 시작 ──
     아이디어 HP = base(장르) × 플랫폼계수 × 시리즈계수
     매 턴:
       - 스태미나 1 소모
       - 배정된 직원이 순서대로 공격
       - 데미지 = 직업기여스탯 × (1 + 의욕×0.005) × 궁합보너스 × 랜덤(0.85~1.15)
       - 데미지가 5개 품질 스탯에 직업별로 누적된다
       - 크리티컬 시 "번뜩임!" 연출 + 품질 보너스
     중간 이벤트:
       - HP 66% 지점 → 게임 내용 아이디어 3장 중 택 1
       - HP 33% 지점 → 개발 방식 아이디어 3장 중 택 1
       - 선택한 아이디어와 장르의 궁합이 최종 품질에 가산
5. HP 0 → 완성. 품질 = (누적 기여) ÷ (턴수 × 팀 인원) 을 포화 곡선에 통과시킨 값.
   인원을 늘리면 개발이 빨라질 뿐 품질은 오르지 않는다.
6. 디버그 (선택) → 버그 제거, 스태미나 소모
7. 출시
```

3D 연출: 직원 캐릭터가 자리에서 일어나 데스크를 두드리고, 말풍선으로 데미지가 튀고,
크리티컬이면 화이트보드에 아이디어가 번쩍인다.

### 3.4 출시와 운영

```
초기 유저 = f(품질 5스탯, 팬 수, 플랫폼 팬층, 수익모델)
평가      = 4인 평론가 점수 (각 1~10)
매출/주   = 유저 × ARPU(수익모델) × 지속성계수
유저 감소 = 지속성 스탯이 높을수록 완만
```

- 동시 **운영 3작품** 상한. 새 작품을 운영하려면 기존작을 서비스 종료해야 한다.
- 평론가 합계가 기준 이상이면 **명예의 전당** 등재 → 속편 제작 해금.
- 속편은 HP·데미지·스태미나 소모가 모두 증가하는 대신 초기 유저가 크게 늘어난다.

### 3.5 사무실

- 층 단위 확장. 각 층에 데스크 슬롯과 시설 슬롯.
- **기획자와 개발자를 다른 층에 두는 편이 유리**하다 (원작 팁 반영).
- 시설(M2 예정): 서버랙(지속성↑), 사운드 부스(사운드↑), 회의실(의욕 회복), 휴게실(스태미나 회복).
  M1 에서는 층별 역할(개발/기획/아트/네트워크)만 기획서 등급에 영향을 준다.

### 3.6 플랫폼 개발

후반 콘텐츠. 자체 소셜 플랫폼을 만들고 콘텐츠 타입을 올린다.
업그레이드는 **개발비↑ · 팬층 변동 · 아이디어 HP↑** 를 동반한다.
플랫폼 지식은 한 번에 하나씩, 가장 값진 타입의 첫 업그레이드에 쓴다.

### 밸런스 (M1 시점, 헤드리스 시뮬레이션으로 검증)

`game/` 은 DOM도 WebGL도 쓰지 않으므로 Node에서 그대로 돌려볼 수 있다.
5년치를 자동 플레이시킨 결과:

| | 신중한 플레이 | 최적 플레이 |
|---|---|---|
| 1년차 | 랭크 6, 14작, 평론 12점 | 랭크 12, 23작, 평론 27점 |
| 2년차 | 랭크 9, 팬 26만 | 랭크 17, 명예의 전당 첫 진입 |
| 5년차 | — | 랭크 18, 평론 33점, 유저 240만 |

조정 과정에서 드러난 세 가지 구조적 함정:

1. **품질을 턴수로만 나누면** 인원수에 비례해 품질이 공짜로 오른다.
   → *1인·1턴당* 기여로 정규화. 사람을 더 넣으면 속도만 빨라진다.
2. **압축 곡선이 없으면** 능력치가 레벨·전직·의욕·궁합·개발방식으로
   곱해지며 네 자릿수를 넘어간다. → 품질과 평론 점수 양쪽에 포화 곡선.
3. **팬 배율에 상한이 없으면** 유저→팬→유저로 스스로를 먹여
   2년차에 차트를 벗어난다. → 상한 6배.

## 5. 디렉터리 구조

```
src/
  core/     math.js  gl.js  color.js  meshbuilder.js  bake.js
  render/   shaders.js  renderer.js  camera.js
  char/     rig.js  poses.js
  world/    palette.js  props.js  office.js
  game/     data.js  state.js  staff.js  project.js  economy.js
  ui/       hud.js  style.css
  main.js
```

- `core/` 는 게임을 모른다. 순수 렌더링 유틸.
- `world/` 는 게임 규칙을 모른다. 지오메트리만 만든다.
- `game/` 는 WebGL을 모른다. 순수 시뮬레이션이므로 그대로 테스트 가능하다.
- `main.js` 가 셋을 묶는다.

이 경계 덕분에 게임 밸런스를 렌더러와 무관하게 고칠 수 있다.
